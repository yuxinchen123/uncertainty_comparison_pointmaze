### The newest installable version is not the one to install

`envpool.make(..., env_type="gym")` — which this script uses — was removed in the 1.x line. From the 1.2.5 wheel's `envpool/registration.py`:

```python
assert env_type in ["dm", "gymnasium"]
```

and it raises on `gym_reset_return_info=False` ("EnvPool's gym API now follows gymnasium reset semantics"). envpool 1.x also drops `gym` from its dependencies entirely and moves Atari ROMs out to separate `envpool-assets*` packages. **envpool 1.x cannot run this script.**

`0.9.0` still has `assert env_type in ["dm", "gym", "gymnasium"]`, still depends on `gym>=0.18`, still bundles ROMs, and even patches `np.bool8` back for old gym under numpy 2. So:

- **Recommended: `envpool==0.9.0`** — newest release that still supports `env_type="gym"`; has cp311/cp312/cp313 wheels; numpy-2 tolerant.
- **Fallback: `envpool==0.8.4`** — contemporaneous with the CleanRL script, so closest to the published PPO-RND benchmark. One-line swap.

Both were run end to end (§7 result below); both pass.

### tyro 0.5.10 is broken on this Python

## 3. The gym constraint

- **`RunningMeanStd` lives in `gym/wrappers/normalize.py` in gym 0.21.0, 0.22.0, 0.23.1, 0.25.2 and 0.26.2** — checked directly in each sdist. So the class is not the binding constraint.
- **The binding constraint is `gym < 0.26`**, because of envpool's version switch (identical code in 0.8.4 and 0.9.0):

  ```python
  new_gym_api = version.parse(gym.__version__) >= version.parse("0.26.0")
  if "gym_reset_return_info" not in kwargs:
      kwargs["gym_reset_return_info"] = new_gym_api
  ```

  With gym ≥ 0.26 envpool switches `reset()` to return `(obs, info)`. The script does `next_obs = torch.Tensor(envs.reset())` (line 320) and unpacks a 4-tuple from `step` (lines 328, 362), so gym ≥ 0.26 breaks it.
- envpool's own metadata asks only for `gym >= 0.18` (`0.6.6`, `0.8.4`, `0.9.0` alike), so envpool imposes no upper bound — the script does.
- **Use `gym==0.23.1`, exactly CleanRL's pin.** Valid window is 0.21.0 ≤ gym < 0.26.
- gym is **sdist-only for every version ever published** (no wheels), so pip has to build it. I build-tested it: `pip wheel --no-deps gym==0.23.1` on Python 3.11 with pip 25.1.1 produced `gym-0.23.1-py3-none-any.whl` with no errors. It is pure Python, `python_requires>=3.7`, deps `numpy>=1.18.0`, `cloudpickle>=1.2.0`, `gym_notices>=0.0.4`.
- **Do not move this env to Python 3.12.** `import gym` pulls `gym.wrappers` → `record_video` → `gym/wrappers/monitoring/video_recorder.py`, which does `import distutils.spawn` and `import distutils.version`. `distutils` was removed from the stdlib in 3.12; it would then work only through setuptools' `distutils-precedence.pth` shim. Python 3.11 has stdlib distutils, so this is a non-issue there.

## 4. numpy

**Pin `numpy==1.26.4`** (same as the `exploration` env; last of the 1.x line).

Evidence:
- envpool **0.8.4**'s `atari_envpool.so` contains only the numpy-1 C-API strings (`_ARRAY_API`, `numpy.core.multiarray`) with no `numpy._core` path. It was built against numpy 1.x headers, so under numpy 2 it fails at import with the usual "compiled using NumPy 1.x cannot be run in NumPy 2.x". **envpool 0.8.4 requires numpy < 2.**
- envpool **0.9.0**'s `.so` carries both `numpy._core` and `numpy.core` plus a `FAILURE obtaining numpy _ARRAY_API pointer` message — built with numpy 2 headers and the backward-compatibility layer, so it tolerates numpy 1.19+ and 2.x.
- gym is numpy-1 era regardless. Importing gym 0.23.1 prints "Gym has been unmaintained since 2022 and does not support NumPy 2.0". It uses `np.float_` (removed in numpy 2) in `gym/envs/classic_control/acrobot.py` — not on this script's import path, but it shows the vintage. envpool 0.9.0 itself compensates with `if not hasattr(np, "bool8"): np.__dict__["bool8"] = np.bool_`.
- Declared floors are permissive: envpool `numpy>=1.19`, gym `numpy>=1.18.0`. torch does not pin numpy at all.

`numpy==1.26.4` satisfies every floor, keeps the 0.8.4 fallback available, and matches what the rest of this project already runs.

## 5. Atari ROMs — bundled, no download, no ale-py, no AutoROM

Inspected the wheel contents directly:

- **`envpool-0.8.4-cp311…whl` and `envpool-0.9.0-cp311…whl` each contain 104 ROM files** under `envpool/atari/roms/*.bin`, including `envpool/atari/roms/montezuma_revenge.bin`. `envpool/atari/registration.py` builds its env list by listing that directory on disk.

Still pip-installable, but another reason 1.x is the wrong line here.

## 8. Risk to the existing `exploration` env

**The two environments are fully separate.** Different prefixes (`/p/rlprojects/RND/.venvs/exploration` vs `.../cleanrl_ppo_rnd_envpool`), different interpreters, different `site-packages`. `conda create --copy` writes no hardlinks, `-p` keeps it out of the conda envs directory, and nothing in the new env writes into the old one. Neither `gym` nor `envpool` exists in `exploration` today, so there is nothing to collide over. `ENVS.md` has no name conflict. Creating the new env cannot change what `exploration` resolves.

**But there is a real problem, and it is not between the two envs — it is `/u/sl5nw/.local`.** I found this while checking the versions quoted in the task:

```
sys.path of /p/rlprojects/RND/.venvs/exploration/bin/python:
  ...
  /u/sl5nw/.local/lib/python3.11/site-packages     <-- comes FIRST
  /p/rlprojects/tinker/tinker-cookbook
  /p/rlprojects/RND/.venvs/exploration/lib/python3.11/site-packages
```

`ENABLE_USER_SITE` is True for conda envs, and the user site directory precedes the env's own. Measured consequence:

| module | what sl5nw sees (default) | what any other user sees (`-s`) |
|---|---|---|
| torch | **2.10.0+cu128** from `/u/sl5nw/.local` | **2.5.1+cu124** from the env |
| gymnasium | **1.2.3** from `/u/sl5nw/.local` | **1.0.0** from the env |
| numpy | 1.26.4 from the env | 1.26.4 from the env |

So the task's description of the canonical env ("torch 2.10.0+cu128, gymnasium 1.2.3") describes what **sl5nw** sees, not what the env contains. `/u/sl5nw/.local` is mode `drwx------`, unreadable by anyone else, so collaborators get the env's real contents — torch 2.5.1+cu124 and gymnasium 1.0.0. The two users are already running different software from the same "shared" env today.

Consequences for the new env, and the mitigations, all folded into §6 and §7 above:

1. **Install-time.** Without `-s` / `PYTHONNOUSERSITE=1`, pip resolves `torch==2.10.0` as already satisfied from `/u/sl5nw/.local` and installs nothing. The env then ships to collaborators with no torch at all, and the failure only appears on their first job. This is the single most likely way to get this wrong.
2. **Run-time.** Without `-s`, sl5nw's jobs use `/u/sl5nw/.local`'s torch and gymnasium while collaborators use the env's — the same command produces different stacks per user.
3. **Not at risk:** `/u/sl5nw/.local` contains **no** `gym`, `envpool`, `numpy`, `tyro`, or `tensorboard` (checked its 187 entries). The two most fragile pins here — old `gym` and `numpy<2` — cannot be shadowed. Only torch, torchvision and gymnasium can.
4. **Recommendation:** put `export PYTHONNOUSERSITE=1` in every sbatch/worker script for this env and invoke as `<env>/bin/python -s`, then note it in the new env's `PROVENANCE.md` and in the collaborator packet. Fixing the same exposure for the `exploration` env is a separate decision and should not be bundled into this work.

One more difference worth knowing: `exploration` injects extra paths through `.pth` files — `/p/rlprojects/RND/07_reconstruction/src` (editable `rnd_exploration`), `/p/rlprojects/tinker/tinker-cookbook`, plus editable IsaacLab packages. The new env will have none of those, so any RND project module the CleanRL work needs must be installed or added on `PYTHONPATH` explicitly.

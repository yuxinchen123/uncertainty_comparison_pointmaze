# Presenting the sweep-scaling measurements

Specification for the figures, tables and headline that turn
`bench_sweep_scaling.py` (studies `rates`, `copies`, `groups`) and `bench_sweep.py`
(layouts `fused`, `separate`, `uniform`) into the sweep-scaling part of the report.
All of it is generated by
`report/2026-08-15-pointmaze-gpu-parallelization/code/make_report.py` — the rendered
`report.md` is never hand-edited.

## Derived quantities used below

Define `t(C)` as the measured seconds per training iteration at `C` copies, `T = 128`
steps and `N = 4` environments per copy (so one iteration is `T * N = 512` environment
steps per copy), `S` as the per-copy step budget, `I` as the iterations that budget
needs, and `H` as the wall-clock hours to finish it:

- iterations for the budget: $I = \dfrac{S}{T N}$ (for `S` = 10 million, `I` = 19,531)
- wall clock: $H = \dfrac{I t(C)}{3600}$, equivalently $H = \dfrac{S}{3600 R}$ with `R`
  the measured per-copy environment steps per second
- environments per second per environment: `per env = per copy / N`, with `N = 4`
- fused-versus-separate advantage at `G` rates and `K` copies per rate:
  $\rho(G, K) = \dfrac{G t(K)}{t(G K)}$

### Figures that would mislead — do not draw them

- **The `groups` study as a curve.** Total copies are held fixed and the number of rates
  never enters the computation (the rate is a `[C]` vector, read the same way whatever
  values it holds), so the line is flat by construction. Drawn next to the growth
  figures it reads as "adding rates is free", when what it actually shows is "splitting
  a fixed copy budget into more rates is free". It goes in Table 3 as numbers, with the
  spread stated against the run-to-run noise.
- **A per-copy or per-environment panel on its own.** Per-copy throughput falls
  gently and looks like a mild penalty, while wall clock for the whole sweep grows
  nearly linearly with the copy count past the knee. The per-copy panel never appears
  without the total panel (Figure 1) and never replaces the wall-clock figure
  (Figure 2), which is the number the user is actually paying.
- **A total-throughput panel on its own.** It rises and then saturates near 7.8e6
  environment steps per second, which reads as "more copies is always better"; past
  saturation the extra copies buy nothing per unit time and the iteration gets
  proportionally longer. Mark the saturation level in the caption.
- **Peak memory on a second y axis** over a throughput curve. Two unrelated quantities
  sharing a frame invite reading their crossing as meaningful. Memory is a table column.
- **The 1.84x single point quoted as a general figure.** One measurement cannot tell
  "the advantage grows with the number of rates" from "the advantage is a constant".
  Quote it only as the 4-rate, 128-copy value until Figure 3 exists.
- **Linear x on any of these.** The measured counts are powers of two; a linear x
  squeezes everything below 1,024 into the left margin.

## Should sweep-versus-separate be extended across the range

Yes. The report has one point (4 rates x 128 copies, fusing 1.84x faster), and one point
cannot distinguish a growing advantage from a constant one — which is exactly the
question behind "what happens when I go to 16 rates".

**Prediction.** The advantage is `\rho(G, K) = G t(K) / t(G K)`, so it is fixed by the
copy-scaling curve and nothing else:

1. It rises while the fused run is still below the knee, because `t` grows sublinearly
   there: from the measured round-2 curve, 1.00 at 1 rate, 1.46 at 2, 1.86 at 4
   (measured 1.84), 2.13 at 8, 2.27 at 16, 2.36 at 32 — at 128 copies per rate.
2. It then flattens near `t(K) / K` divided by the marginal per-copy cost at
   saturation — about 2.4x for 128 copies per rate. Once the fused run also fills the
   GPU, both layouts scale linearly in total copies and the ratio stops moving.
3. The ceiling is set by how far one group alone is from filling the GPU, not by the
   number of rates: about 27x for 8 copies per rate, about 2.4x for 128, and about 1.3x
   for 512, where one group already uses much of the GPU. These are asymptotes, reached
   only once the fused total is itself saturated (about 8,192 copies), so within 32
   rates the 8-copies-per-rate curve will still be climbing, not flat.

**Measurement that establishes it.** Run `bench_sweep.py` at rate counts 1, 2, 4, 8, 16,
32 for copies-per-rate 8, 128 and 512 (skip the combinations over the memory ceiling),
in the same process-level ABBA order used for the round-2 comparisons, and plot the
measured ratio against `G t(K) / t(G K)` computed from the copy-scaling curve. Agreement
within the noise floor establishes that the whole advantage is the copy-scaling curve and
no separate mechanism is involved. The `separate` timing is a sum over groups by
construction, so measure it directly at two rate counts per `K` to confirm it really is
additive (no per-trainer setup or memory-reuse cost leaking in) and derive the rest.
